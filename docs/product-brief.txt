⸻

A. PRODUCT MISSION

MedMemory is a patient-owned digital memory of a person’s medical history.

It should securely transform scattered medical records into a structured, searchable, traceable longitudinal health archive.

Users should be able to upload:

* prescriptions
* laboratory reports
* discharge summaries
* diagnostic reports
* scanned documents
* medical PDFs
* photographs of records

MedMemory should preserve the original record while producing:

* OCR text
* normalized document representation
* structured medical information
* longitudinal events
* search
* evidence-backed questions and answers
* doctor handoff summaries
* configurable emergency information
* secure temporary sharing

The product must prioritize:

1. privacy
2. correctness
3. provenance
4. reversibility
5. user control
6. failure transparency

This is NOT a diagnosis engine.

Never fabricate medical facts.
Never create fake medical history.
Never infer diagnoses that are absent from evidence.
Never silently alter original records.

⸻

B. NON-NEGOTIABLE ENGINEERING PRINCIPLES

Follow these rules throughout the entire build.

B1. Repository-first behavior

Before making changes, run and inspect:

* pwd
* ls / directory tree
* git status
* git branch
* package files
* existing source
* existing migrations
* environment templates
* Python environment if present

Determine whether:

* the repo is empty
* partially built
* contains unrelated work
* contains an older MedMemory attempt

Never overwrite unrelated files.

If existing MedMemory code is broken, preserve useful pieces only when they satisfy the new architecture.

Prefer clean replacement over layering hacks onto broken abstractions.

⸻

B2. No fake completion

Never:

* create mock success responses and call a feature complete
* hardcode demo medical information into production paths
* return invented values when extraction fails
* mark processing completed when only part of the pipeline succeeded
* swallow exceptions
* claim tests passed without running them

⸻

B3. Error transparency

Every meaningful failure must result in:

* structured log
* useful internal error code
* correct HTTP status
* persisted processing error where appropriate
* safe user-facing explanation

Never use empty catch blocks.

Never use patterns like:

catch {
  return false
}

without explicit handling.

⸻

B4. Security is server-enforced

Frontend authorization is never sufficient.

Every sensitive resource must be protected by:

* authentication
* server-side authorization
* Supabase RLS
* private storage policies

⸻

B5. Local-first AI

The core product must not depend on paid AI APIs.

Base functionality:

OCR:

* PyMuPDF
* Tesseract
* OpenCV

Structured extraction:

* deterministic parser
* regex
* optional Ollama

QA:

* retrieval
* local Ollama when available
* deterministic evidence fallback

Ollama unavailability must degrade gracefully.

G. RLS CONTRACT

Policies must enforce:

user_id = auth.uid()

for user-owned data.

Users cannot:

* select other users’ rows
* insert using another user_id
* update another user’s rows
* delete another user’s rows

For child tables, either duplicate user_id for strong policy simplicity or safely derive ownership through parent relations.

Never depend on hidden frontend IDs.

Write security tests.

Minimum test:

User A creates a document.

User B attempts:

SELECT
UPDATE
DELETE
child-table access

All must fail.

L. PDF PROCESSING

For PDFs:

1. open using PyMuPDF
2. inspect native text page by page
3. calculate whether native text is usable
4. if usable:
    * preserve native text
    * derive blocks if possible
    * skip OCR for that page
5. otherwise:
    * render high-quality image
    * preprocess
    * OCR

Do not OCR a clean digital PDF unnecessarily.

Do not treat a PDF as either all-native or all-scanned if pages differ.

Decision can occur page-by-page.

AX. BUG-FIXING PROTOCOL

When a command fails:

1. capture exact error
2. determine subsystem
3. inspect relevant source
4. identify root cause
5. implement smallest correct fix
6. rerun targeted test
7. rerun broader gate if necessary

Do not:

* randomly install packages
* weaken types
* disable tests
* bypass RLS
* comment out failing functionality
* replace real code with mocks

to obtain green builds.

BR. PREVIOUS FAILURE DEFENSES

Explicitly test against these historical failure classes:

1.

Code references DB columns that migrations do not contain.

Defense:
generated DB types + typecheck + migration audit.

2.

Upload succeeds but processing trigger fails silently.

Defense:
persist processing job transactionally and expose job state.

3.

Cloud AI key unexpectedly required.

Defense:
cloud providers absent from default dependency path.

4.

Fallback returns fake diagnosis/demo data.

Defense:
test no-evidence flows and ban fixture imports from production.

5.

OCR finds incomplete values and extraction invents remainder.

Defense:
provenance requirement + extraction validation.

6.

Provider label says local OCR while another implementation executed.

Defense:
provider metadata comes from runtime provider result, not hardcoded UI string.

7.

Document status says complete despite downstream persistence failure.

Defense:
explicit state machine and transactional persistence.

8.

RLS missing on one new medical child table.

Defense:
security test enumerates protected tables.

9.

Reprocessing duplicates results.

Defense:
fingerprints + uniqueness + reprocess tests.

10.

Source references lost after structured normalization.

Defense:
provenance fields mandatory and acceptance test.
